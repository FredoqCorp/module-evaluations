# CascVel: backend модуля «Оценка»

Дата: 2026-09-05. Статус: разделы согласованы, документ ожидает итогового просмотра.

## 1. Назначение и границы

Модуль обеспечивает экспертную оценку качества работы операторов по обращениям: подготовку оценочных форм, проведение и публикацию оценки, ознакомление оператора и рассмотрение запроса пересмотра.

Объект оценки — работа конкретного оператора в конкретном обращении. Для сочетания «обращение + оператор + форма» существует одна оценка с историей редакций. Разные формы позволяют независимо оценить разные стороны этой работы. Версия формы не входит в ключ уникальности оценки.

Выбран один автономный backend с собственной БД и интеграцией через API и события. Встраивание в общий backend платформы и разделение форм, оценок и пересмотров на отдельные сервисы рассмотрены и не выбраны: первое связывает модуль с будущей архитектурой платформы, второе добавляет ненужные сейчас межсервисные взаимодействия.

Первая версия работает в пределах одной установки CascVel. Обращения, история общения, пользователи и доставка уведомлений принадлежат внешним модулям. Оценка клиентов после обслуживания, автоматические критерии по KPI, ограничения доступа специалистов по командам и очередям, независимые оценки нескольких экспертов по одной форме не входят в первую версию.

Модуль проектируется самостоятельно; совместимость с API, схемами БД и файловыми форматами других продуктов не требуется.

## 2. Термины и ответственность

| Понятие | Назначение |
| --- | --- |
| Форма | Постоянная идентичность методики оценки, объединяющая её версии |
| Версия формы | Конкретные группы, критерии, шкалы и веса методики |
| Критерий | Один аспект работы, оцениваемый экспертом вручную |
| Шкала | Набор вариантов ответа с числовыми баллами и границами нормализации |
| Оценка | Проверка работы оператора в обращении по одной форме и закреплённой версии |
| Редакция оценки | Опубликованные ответы, комментарии и рассчитанный результат на определённый момент |
| Запрос пересмотра | Несогласие оператора с конкретной опубликованной редакцией и решение специалиста |

Формы отвечают за методику и пригодность версии для новых оценок. Оценки используют неизменную опубликованную версию, хранят контекст и ответы. Пересмотры относятся к опубликованным редакциям оценки и сохраняют решения. Это части одного приложения, а не отдельные сервисы.

## 3. Формы и версии

Новая версия создаётся как редактируемый черновик. Она содержит группы без вложенных групп; каждая группа содержит критерии. У каждого критерия выбрана шкала и указано, разрешён ли ответ «Не применимо».

Для публикации версия должна содержать хотя бы одну группу, а каждая группа — хотя бы один критерий. Веса групп и критериев положительны. Сумма весов групп равна 100%; сумма весов критериев внутри каждой группы также равна 100%. В черновике допускается неполная структура; публикация выполняет полную проверку.

После публикации содержание версии неизменно. Публикация следующей версии заменяет предыдущую для новых оценок. Пока новая версия остаётся черновиком, для новых оценок используется прежняя опубликованная версия.

Архивирование формы запрещает создание новых оценок по ней. Существующие оценки доступны для завершения, просмотра и пересмотра. Архивирование не удаляет версии или историю. Восстановление формы из архива не входит в первую версию.

Существующая оценка всегда использует исходную версию, в том числе при пересмотре. Перевод оценки на новую версию формы и создание второй оценки той же работы по новой версии не допускаются.

## 4. Шкалы и расчёт

В первой версии доступны две встроенные шкалы:

| Шкала | Варианты и баллы | Нормализованные значения |
| --- | --- | --- |
| Числовая | 1, 2, 3, 4, 5 | 0, 25, 50, 75, 100% |
| Бинарная | «Нет» = 0, «Да» = 1 | 0, 100% |

Модель шкалы предусматривает идентифицируемые варианты ответа, их баллы и границы нормализации. Управление пользовательскими шкалами не реализуется в первой версии. Изменение каталога шкал в будущем не должно менять смысл опубликованных версий форм или исторических ответов: используемое определение шкалы закрепляется в версии формы.

Нормализованный балл критерия:

`score = 100 × (value − minimum) / (maximum − minimum)`

Максимум шкалы должен быть больше минимума, баллы вариантов должны находиться в этих границах, выбранный ответ должен принадлежать закреплённой шкале. Клиент передаёт вариант ответа; балл и итог определяет backend.

Для каждой группы вычисляется взвешенное среднее применимых критериев:

`groupScore = sum(criterionWeight × score) / sum(criterionWeight)`

Итог формы — взвешенное среднее непустых после исключения групп:

`total = sum(groupWeight × groupScore) / sum(groupWeight)`

Суммы в формулах включают только участвующие в расчёте критерии и группы. Вес критериев влияет на результат внутри группы, вес группы — на общий результат.

«Не применимо» разрешено только настройкой критерия и требует непустого обоснования. Такой ответ исключает критерий из расчёта, пропорционально перераспределяя вклад оставшихся критериев группы. Если все критерии группы исключены, из общего расчёта исключается и группа. Если исключены все группы, итог отсутствует и публикация запрещена.

Незаполненный ответ отличается от «Не применимо»: он допустим в черновике, но блокирует публикацию. Для публикации каждый критерий должен иметь допустимый ответ либо разрешённое исключение с причиной.

Расчёты выполняются в `decimal` без намеренного округления промежуточных результатов. Итог округляется до двух знаков: до ближайшего значения, в середине — от нуля. Округлённые значения групп не используются для вычисления общего результата.

### Пример для проверки

Группа A имеет вес 60% и два критерия с весами 25% и 75%. Ответ 3 по шкале 1–5 даёт 50%, ответ «Да» — 100%. Результат группы A равен 87,5%. Группа B с весом 40% имеет результат 50%. Итог формы равен 72,50%.

Если второй критерий группы A отмечен «Не применимо», результат A равен 50%, итог — 50,00%. Если исключена вся группа A, итог определяется только группой B и равен 50,00%. Если исключены все критерии обеих групп, публикация запрещена.

## 5. Создание и публикация оценки

При создании оценки сервис обращается к API модуля обращений и подтверждает два условия: обращение завершено, выбранный оператор участвовал в его обработке. Проверка выполняется с ограниченным временем ожидания. Недоступность зависимости или неподтверждённые условия не создают оценку.

С оценкой сохраняются идентификаторы обращения и оператора, подтверждённые сведения о завершении, время проверки и выбранная опубликованная версия формы. Модуль не копирует историю общения. Выбранная версия должна оставаться доступной для новых оценок в момент фиксации создания; конкурентное архивирование или замена версии не обходят это правило.

Переоткрытие обращения после подтверждения не блокирует заполнение и публикацию оценки. Она относится к работе до завершения, зафиксированного при создании. Повторная проверка текущего статуса перед публикацией не требуется.

Эксперт заполняет черновик и сохраняет незавершённую работу. Предусмотрены комментарии к ответам и к оценке. До первой публикации оператор не видит оценку.

При публикации backend проверяет ответы, вычисляет итог и сохраняет опубликованную редакцию с автором и временем. Опубликованные редакции не перезаписываются. Исправление опубликованной оценки в первой версии выполняется через согласованный процесс пересмотра.

## 6. Ознакомление и пересмотр

Просмотр опубликованной редакции фиксируется отдельно от согласия. Оператор может согласиться с ней либо запросить пересмотр, указав непустую причину. Действия относятся к конкретной редакции: устаревший запрос не должен автоматически применяться к более новой редакции.

Любой специалист с правом пересмотра, включая автора оценки, может рассмотреть запрос. Возможны два решения:

1. Оставить оценку без изменения и записать обязательное обоснование.
2. Изменить ответы по исходной версии формы, проверить их, пересчитать результат и опубликовать новую редакцию с обязательным обоснованием.

Пока изменения готовятся, оператор видит последнюю опубликованную редакцию. Промежуточная работа специалиста не меняет опубликованный результат.

При оставлении оценки без изменения запрос закрывается. Несогласие и решение сохраняются в истории; второй запрос по той же редакции недоступен. Это не означает автоматического согласия оператора.

При изменении оценки запрос закрывается с привязкой к новой редакции. Для новой редакции ознакомление и ответ оператора начинаются заново; прежние сведения остаются в истории. Оператор может запросить пересмотр новой редакции. Одновременно для одной редакции не создаются несколько запросов.

История содержит опубликованные редакции, ответы, комментарии, результаты, авторов и даты публикаций, просмотры и ответы оператора, причины запросов и обоснования решений. Полный журнал каждого изменения черновика не требуется.

Аннулирование оценки не входит в согласованные исходы пересмотра первой версии.

## 7. Доступ

Внешний провайдер CascVel аутентифицирует пользователя. Модуль проверяет токен и полномочия; идентификатор автора берётся из подтверждённой личности, а не из поля запроса. Данные о пользователях и выдача полномочий не управляются этим модулем.

| Полномочие | Доступные действия |
| --- | --- |
| Управление формами | Создание и изменение черновиков, создание версий, публикация и архивирование форм |
| Проведение оценки | Создание, заполнение и публикация оценок, просмотр результатов |
| Пересмотр | Просмотр необходимых материалов, обработка запросов и публикация решений |
| Оператор | Просмотр только своих опубликованных оценок, ознакомление, согласие и запрос пересмотра |

Полномочия могут совмещаться. Право проведения оценки само по себе не даёт права пересмотра. Специалисты работают со всеми соответствующими данными в пределах одной установки CascVel; ограничений по командам и очередям в первой версии нет.

Проверка принадлежности оценки оператору обязательна при чтении списков и отдельных объектов и при каждом действии. Черновик первоначальной оценки и неопубликованные изменения при пересмотре оператору недоступны.

## 8. API, данные и события

API покрывает формы и версии, создание и заполнение оценок, публикацию, чтение результатов и истории, ознакомление, согласие, запрос и решение пересмотра. Списки результатов поддерживают фильтрацию и постраничную выдачу. Конкретные маршруты и DTO определяются в плане реализации в рамках этих операций.

PostgreSQL обеспечивает уникальность сочетания «обращение + оператор + форма». Повтор или одновременное создание не порождают вторую оценку. Конфликт возвращается явно.

Сохранение изменяемых данных и переходы состояния проверяют ожидаемую версию записи. Конкурирующий запрос со старой версией отклоняется без перезаписи чужой работы. Это относится в том числе к публикации версии формы, публикации оценки и разрешению пересмотра.

Редакция, ответы, итог, история, закрытие запроса пересмотра при наличии и соответствующие события outbox сохраняются одной транзакцией. При решении изменить оценку нельзя закрыть запрос без публикации новой редакции. При решении оставить оценку без изменения одной транзакцией сохраняются решение, обоснование, закрытие запроса и событие; новая редакция не создаётся.

Через RabbitMQ передаются события о публикации редакции оценки, создании запроса пересмотра и решении по нему. Каждое событие имеет стабильный идентификатор, тип и версию контракта, время, идентификаторы оценки и соответствующей редакции или запроса. Событие позволяет получателю определить опубликованное изменение без обращения к незафиксированному состоянию.

MassTransit доставляет события из outbox с повторными попытками. Ошибка брокера не теряет событие и не отменяет уже зафиксированную оценку. Доставка допускает повторы; потребители обрабатывают их идемпотентно. Нельзя полагаться только на порядок получения событий: редакция и идентификаторы связывают события с нужным состоянием.

Уведомления операторам доставляет внешний модуль на основании событий. До его подключения результаты доступны через API модуля оценки.

API различает ошибки входных данных, отсутствие аутентификации или полномочий, отсутствие доступного объекта, конфликт состояния и недоступность внешней зависимости. Ошибки возвращаются в едином структурированном формате с контекстом для исправления или повторения запроса, без секретов и внутренних технических подробностей.

## 9. Технологии и проверка

Один процесс ASP.NET Core 10, C# 14, PostgreSQL 18, MassTransit и RabbitMQ. Redis не требуется для согласованных сценариев. Реализация не требует новых сервисов, собственного механизма доставки событий или универсального движка процессов.

Разработка ведётся через TDD. Проверки бизнес-правил предшествуют реализации; интеграционные проверки используют реальные PostgreSQL и RabbitMQ. API обращений заменяется управляемым локальным тестовым сервером. Тесты не требуют внешнего Интернета, используют временные порты и ограниченные ожидания; логирование в тестах отключено.

Обязательные группы проверок:

- Расчёт обеих шкал, двух уровней весов, нормализации, округления и примера из раздела 4; исключение критериев и групп; запрет публикации без оцениваемых ответов.
- Публикация неполной формы, неверные веса и ответы, неизменность опубликованной версии, замена версии для новых оценок и архивирование.
- Создание только после подтверждения завершения и участия оператора; ошибка и тайм-аут зависимости; завершение оценки после переоткрытия обращения.
- Сохранение исходной версии при пересмотре, обязательные причины и обоснования, история, повторное ознакомление и ограничения повторных запросов.
- Недоступность чужих оценок и черновиков оператору; независимость полномочий управления формами, проведения оценки и пересмотра.
- Конкурирующее создание и редактирование, устаревшие команды ознакомления и пересмотра, атомарность публикации и outbox, сбой брокера и повторная доставка событий.

Критерий готовности первой версии: специалист создаёт и публикует форму, оценивает работу оператора в завершённом обращении, оператор знакомится и запрашивает пересмотр, уполномоченный специалист публикует решение; история, доступ, расчёт и события сохраняют описанные гарантии.

## 10. Следующий этап

После итогового просмотра документа составляется план реализации с последовательными проверяемыми частями: формы и расчёт, проведение оценки, ознакомление и пересмотр, интеграции и проверка полного сценария. Каждая часть реализуется в рамках этой спецификации. Код и инфраструктурные конфигурации настоящим документом не создаются.
